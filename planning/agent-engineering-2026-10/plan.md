## 1. 推荐路线与完成标准

推荐沿现有 FastAPI、LangGraph、Next.js 和 SQLite 架构，完成一条能够演示、解释失败原因并复跑评测的教学 Agent 链路：

> 学生请求 → 确认任务 → 检索教材与任务状态 → 受控工具 / 数值规则 → 教学回答 → 交付检查 → 保存结果与执行回执。

用户已确认“可靠性与评测优先”。第一里程碑 **A1 交付检查 + A2 执行追踪 + A3 离线评测** 已完成本地工程验收。后续推荐 **A4.1 当前任务 → A6.1/A4.2 业务动作、卡片与内嵌聊天 → A6.2 计算工具及旧代码路径退役 → A7 调用计量 → A5 行为 / 真实评测**；A8 有条件启动。先打通 Newton 实验到聊天的产品闭环，已有线性/积分实验保留并后续复用合同。每批独立验收，不增加第二套工具 Registry。

第一里程碑完成时，应该可以用一次成功回答、一次输出截断、一次工具超时、一次取消和一次交付拦截，回答以下问题：

- 系统实际走了哪些步骤，在哪一步失败？
- 为什么允许、修复或拦截这条回答？
- 用户刷新后看到的状态是否与服务器一致？
- 重试会不会重复写学习记录、重复执行工具？
- 哪些结论来自确定性规则，哪些只是模型意见？

衡量价值的主线是可靠执行与证据闭环。Agent 数量、框架数量和提示词长度不设为成果指标。

## 3. 参考成熟 Agent 项目，如何落到本项目

参考范围是代表性项目的官方文档，不是按 GitHub 星标作排名。以下“项目建议”是结合本仓库约束的设计判断，不是这些框架自动保证的能力。

| 参考 | 官方设计 | 本项目采用的思路 | 适用边界 |
| --- | --- | --- | --- |
| [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence) | checkpointer 保存 thread 状态；store 保存跨 thread 信息 | 分清执行状态、对话历史和学习事实的权威来源 | 当前 SQLite 已持久化历史；不要叠加 RAM MemorySaver 当生产记忆。真正恢复执行需幂等协议 |
| [OpenAI Agents SDK Guardrails](https://openai.github.io/openai-agents-python/guardrails/) | 输入、最终输出和函数工具调用有不同检查边界 | A1 放在最终正文发送之前，工具输入继续走现有 AST 检查 | Guard 通过不代表数学证明正确，也不替代 owner 校验 |
| [OpenAI Agents SDK Tracing](https://openai.github.io/openai-agents-python/tracing/) | 用 trace / span 描述模型、工具与检查；可关闭敏感输入输出采集 | A2 默认只记录本地白名单元数据，关联 run、步骤和终态 | 不持久化私有思维链、密钥或完整提示词，不默认上传第三方 |
| [Dify LLM 节点](https://docs.dify.ai/en/cloud/use-dify/nodes/llm) | 结构化输出、重试参数、失败路由与回退 | 结果契约、失败分类、有限恢复预算 | 不把失败变成假答案；产生副作用之后不盲目重跑整个图 |
| [Letta Memory Blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks) | 记忆块有明确用途，支持只读块 | A4 给任务上下文标明来源、版本、用户声明 / 推断和读写权 | Agent 不得自己改教师教材、独立成绩、原始事件或权限 |

先不迁移框架：当前主要缺口在交付、状态和验收协议，换 SDK 会增加迁移成本，也不能自动补上教学规则。只有现有 LangGraph 无法满足一个已验证需求时，再独立评估迁移。

1. **正常完成必须有依据。** 流式收到成功终止标志且存在正文才通过；`length`、`content_filter`、不支持的原生工具调用、损坏 JSON、服务端错误和无终止 EOF 使用有界错误码。非流式兼容通道检查已有 `finish_reason`；缺少它时仍允许结构完整的正文，后续真实提供方烟测确认兼容性。

5. **取消有进程所有权。** 执行器持有子进程句柄；取消或超时杀掉子进程、完成通信回收并删除临时脚本。AST allowlist 未放宽。

## 5. 第一里程碑设计：让一次 Agent 运行可检查、可解释、可复跑

A1–A3 已完成本地工程验收；以下保留设计与验收目标，实际覆盖和延后项以两份交付回执为准。

### A1：最终交付检查与一次修复预算

**用户变化：** 工具没有执行、来源不足或回答越过教学边界时，不会直接收到一条看似已验证的答案；界面明确表示“已修复表述”或“本轮未交付”。

**最小实施：** 在 `_stream_generation` 得到可见候选正文之后、发送 `message` 之前增加 `answer_guard.py`。Teacher / Examiner / Proof 共用；受控求根诊断保留自己的规则与显示 ACK，另加只读契约检查，不让模型改写 Oracle 结论。

首批规则控制在四类：空正文 / 内部协议残留、与执行证据矛盾的“已运行代码”声称、把工具执行成功说成整段数学结论已验证、练习模式未获请求就披露完整解答。引文、否定句、代码示例必须有反例测试，避免简单关键词拦截正常讲解。涉及数学语义且不能确定的内容标成未核验，不假装规则已证明它错。

输出契约：`scope=delivery_rules_only`；`status=passed|repaired|withheld|unavailable`；带规则版本、规则 ID、修复次数，禁止把该状态直接写进 `verified=true`。

**恢复预算：** 最多一次仅文本修复调用，不再执行工具、不新增尝试、不更新成绩。修复后再次检查；仍不通过或检查器异常，安全失败并保存失败回执，不发送候选正文。现有缓冲机制支持前置检查；这一切片先保留缓冲，不同时改成边生成边显示正文。

**验收：** 原始候选不提前进入 SSE / 历史；一次修复上限；第二次违规 withheld；检查器失败不降级为 passed；合法引文与否定不误拦；工具失败不能被文字“修复”成成功。

预计 1–2 个集中开发日。无新数据库表或第三方依赖。独立开关关闭新增检查时仍保留 A0 的失败与空正文门控。

### A2：持久执行记录与可理解的进度

**用户变化：** 回答旁可以折叠查看“确认任务 → 查找教材 → 计算核对 → 检查回答”的执行记录；失败标出阶段，刷新后仍能查看。记录表达公共动作，不展示模型思维链。

**最小实施：** 用 stdlib UUID 和现有 Repository 新增 `agent_runs` 表，记录 owner、session、run_id、message_id、状态、版本、时间、有限步骤 JSON。会话历史仍是对话权威来源，run 表只管理执行回执。步骤使用递增 seq，最多 64 条，超量记录截断标志；按版本 / seq 原子更新，终态禁止被旧事件覆盖。

状态：`running → succeeded|clarification|failed|cancelled|interrupted`。取消写 cancelled；重启后过期 running 标 interrupted，不能补造 done。只允许已完成的记录回看；“重新尝试”创建新 run，关联原 run，不自动重放已经执行的副作用。

SSE 增加有版本的执行事件；前端忽略未知版本，保留旧历史兼容。元数据白名单包含阶段、状态、轮次、耗时、错误码、模型别名、usage（提供方缺失则 null）。不保存提示词、tool code/stdout、密钥、供应商错误正文、上传内容或私有推理；已有业务会话保存策略不借此扩大。

**验收：** 取消 / 超时 / 刷新 / 重启 / 重复事件 / 越权读取 / 并发终态；终态与消息结果一致；无敏感数据；390px 与桌面可读。DB 迁移须备份、临时库复跑并验证旧库；表只增不删，回滚代码保留新表数据。

涉及 `memory/repository.py`、数据库初始化 / 迁移现有入口、`tutor/orchestrator.py`、图节点、`api/routes_sessions.py`、`web/lib/api.ts` 和聊天消息组件。新增内部类型与 schema 版本独立于教学 prompt 版本。

预计 2–3 个集中开发日。是否增加 provider 首 token 指标在这一切片处理：真实首正文 token、缓冲完成、可见正文开始和总耗时必须分开命名。

### A3：离线失败注入评测与 CI 门控

**用户变化：** 无须模型 Key 就能复跑一个能展示 Agent 失败行为的评测命令；失败样例可以用于面试讲解。

**最小实施：** 复用本轮 fixture，建立版本化 case manifest 和 `scripts/eval_agent_reliability.py`，结果写入 ignored `results/`；提交案例、执行代码、汇总回执与源文件哈希，不提交学生数据。

至少覆盖：正常完成、半途 EOF、输出截断、空正文、服务端错误、不确定意图、路由变更、工具失败、成功但无输出、超时、取消、交付修复、交付拦截、记录失败。对有状态的案例走实际编译图 / Orchestrator / 临时 SQLite，避免仅测试一个 mock 自己的断言。

统计指标分别定义：异常假完成数、错误被正确分类的比例、未澄清触发学习写入数、取消后存活子进程数、重复事件产生的重复写入数、守卫误拦数。每项公开分子、分母、fixture 范围；确定性协议案例要求零假完成、零越权 / 重复写入，不把通过率叫模型准确率。

先用固定案例跑通后再冻结第一版；案例覆盖变化时升版本。报告中记录 Git SHA、环境、案例哈希、命令、耗时与失败列表。CI 继续离线；不把真实 API 或 flaky 外网加入 `npm test`。

**验收：** 一条命令得到相同语义结果；破坏终止门控 / 取消处理 / guard 时至少相应案例失败；日志字段缺失与 fixture 错误也使命令退出非零。计时可变，语义与统计口径必须稳定。

预计 1–2 个集中开发日。与 A1 / A2 分批交付，指标以实际结果填写。

## 6. 第二里程碑：提升教学任务连续性和模型质量证据

### A4：跨功能任务上下文与可纠正记忆

验收覆盖：实验版本变更、删除 / 不属于当前用户、陈旧链接、跨会话、上下文超预算、独立帮助拦截、刷新和用户纠正。对照不含 snapshot 的基线，评测“任务引用正确率 / 版本错误率 / 不必要追问”，不预设提升幅度。

对同一冻结集比较帮助边界修复后的 `612e3a4` 基线与实际交付的 A4/A6/A7 候选，只比较双方支持的任务及同一模型/配置；新增能力覆盖单列。E0协议、E1工具/路由行为、E2数学/教学质量、E3跨页面多轮任务分开，口径见 [Runtime合同](runtime-review-schedule.md#4-各阶段可验收的结果)，新交互负例见 [聊天衔接验收](chat-workspace-review.md#6-验收回滚与演示)。报告任务遵循、版本引用/动作正确性、证据一致、Guard误拦、调用数、usage覆盖率与延迟。缺用量保留null，不补造成本；小样本延迟只报告测量范围。人工数学gold独立核对，不让同一个LLM自评作为唯一依据。
